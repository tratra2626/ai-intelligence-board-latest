Agent 这一层，为什么近一年变得更重要

Agent 可以简单理解为“能够围绕目标持续调用工具、读取环境、管理状态并执行多步动作的模型系统”。这一定义不要求它完全自主，但强调它不是一次性回答，而是可以完成连续任务。

Agent

Agent 在这里具体指什么

在当前行业语境里，agent 通常指一种可持续执行任务的模型系统。它会围绕目标进行多步处理，而不是只返回一次答案。典型能力包括调用工具、读取外部数据、保持状态、拆分步骤、处理异常和在必要时等待下一次触发。

因此，讨论 agent 时，重点通常不在“它会不会聊天”，而在“它能否持续完成工作”。这也是为什么很多公司开始把模型、工作流、调度器和连接层一起打包成新的产品层。

OpenClaw

OpenClaw 更像多渠道入口和控制平面

从官方 GitHub 和文档看，OpenClaw 的核心特点是本地优先的 gateway、跨渠道接入和统一控制面。它强调的是：同一个 agent 可以连接 Telegram、Slack、Discord、Feishu、WebChat 等多个入口，并通过 dashboard、skills、sessions 和 routing 做统一管理。

因此，OpenClaw 的价值更偏“分发和运营层”。如果团队关注的是多平台消息接入、统一会话控制、技能安装和设备/浏览器能力调用，那么 OpenClaw 提供的是一套更接近 control plane 的产品形态。

Hermes 更强调 memory、learning loop 和 agent runtime

Nous Research 的官方仓库把 Hermes 描述为 “the self-improving AI agent”。从公开文档看，它最强调的几个点是：持久记忆、跨会话检索、技能自我改进、定时任务、子代理并行，以及可在多种终端或消息入口上长期运行。

这意味着 Hermes 的核心卖点更偏“agent 本体”。相比把渠道和控制面放在第一位，它更强调 agent 在长期运行中的学习、记忆和任务延续能力，也因此更容易被讨论为一类 agent runtime 或 agent OS。

参考：NousResearch Hermes Agent GitHub
对比

OpenClaw 和 Hermes 的差异可以怎么理解

一个相对稳妥的理解方式是：OpenClaw 更偏“gateway-first / control-plane-first”，Hermes 更偏“agent-first / runtime-first”。两者并非完全对立，也有大量能力重叠，但产品重心不同。

如果关注的是跨平台入口、路由、会话管理和统一控制，OpenClaw 的框架更容易理解；如果关注的是记忆、技能积累、自我改进和长期任务连续性，Hermes 的叙事会更突出。行业层面，这也说明 agent 竞争已经开始分化为不同产品路线，而不只是模型路线。

影响

为什么这类项目值得关注

第一，它们反映了市场正在从“调用模型”走向“部署 agent 系统”。第二，它们把模型之外的价值层显性化，包括入口、记忆、路由、治理、技能分发和长期运行。第三，它们说明 agent 产品未来未必会被单一模型厂商完全垄断，中间层和控制层仍有独立产品空间。

对头部公司来说，这种变化会推动更多平台能力内建化；对创业项目来说，则意味着仍然可以围绕 runtime、workflow、control plane 或垂直入口建立产品差异。

看这个专题时最该记住什么

Agent 并不只是“更智能的聊天机器人”，而是一个能持续调动工具、保持状态并执行多步任务的系统。围绕 agent 的竞争，正在从模型本身扩展到 runtime、gateway、memory、skills 和治理能力。

OpenClaw 和 Hermes 可以看作两条不同重心的产品路线：前者更偏控制平面和多入口，后者更偏 agent runtime 和长期记忆。这种分化本身就是当前 agent 市场成熟度提升的信号。

本期专题 MCP / Context / Harness 围绕 AI 工程范式演进的基础概念梳理：先看定义，再看它为什么重要。

MCP 和 Harness 到底在解决什么问题

这条演进线可以概括为三步：先优化单次交互，再管理多轮上下文，最后把模型纳入可治理、可评测、可连接外部系统的完整执行框架。下面按这个顺序展开。

Prompt

Prompt engineering 是什么

Prompt engineering 的核心是优化输入表达，让模型更稳定地理解任务目标。常见做法包括明确角色、输出格式、边界条件、语气要求，以及提供少量示例。

它在早期非常有效，因为当时很多应用仍以单轮问答或单步生成任务为主。问题在于，当任务开始涉及多步处理、外部数据、工具调用和连续状态时，提示词本身不再足以承载全部控制逻辑。

参考：OpenAI Prompt Engineering Best Practices
Context

为什么行业会升级到 context engineering

随着应用复杂度提升，模型需要处理的不再只是一个问题，而是一组与当前任务相关的信息。这里的 context 包括聊天历史、文档片段、数据库结果、工具返回值、用户状态、权限范围和中间步骤结果。

Context engineering 关注的是：哪些信息应当进入当前上下文，如何排序，如何压缩，何时保留历史，何时丢弃噪音。它直接影响响应质量、推理成本和系统稳定性，因此已经成为企业级 AI 应用的关键工程环节。

参考：Anthropic Long Context Tips
Harness

Harness 是什么

Harness 不是单一协议，而是更偏工程实践的说法。它指模型外层的执行框架，包括任务编排、工具调用、权限控制、失败重试、状态管理、日志追踪、评测与回退机制。

当应用从“生成一段内容”转向“调用多个系统完成一个流程”时，差异化优势往往不再只来自模型能力，而来自 harness 是否足够稳定、可观测、可审计。也正因如此，很多头部厂商正在把这部分能力产品化。

参考：OpenAI Agent Evals
MCP

MCP 在这条链路里的位置

MCP 是一类面向模型与外部工具/数据源连接的开放协议。它试图把原本高度定制化的连接过程标准化，让模型客户端、工具服务和外部资源之间形成更统一的交互方式。

它的重要性不在于直接提升模型智能，而在于降低集成成本、扩大工具生态，并提高模型进入企业系统的效率。如果这类协议形成规模效应，平台竞争就会从单一模型能力扩展到连接标准和生态组织能力。

参考：Anthropic MCP Docs
影响

对 OpenAI、Anthropic、Google 这类头部公司的影响

第一，竞争焦点会从模型能力本身，转向更完整的 agent 基础设施能力。第二，连接器、评测、权限治理和工作流管理，会逐渐从附属功能变成主产品的一部分。第三，客户迁移成本会提升，因为企业真正接入的是一整套流程，而不是单个聊天入口。

从商业角度看，这通常意味着收入结构更平台化：除了 token 计费，厂商还会围绕连接、评测、治理和企业工作流形成新的产品层。长期看，这类能力可能比单次 benchmark 优势更接近可持续护城河。

参考：OpenAI Evals Guide
结论

可以如何理解这一轮演进

如果只关注模型版本更新，很容易低估 AI 工程层面的变化。当前更重要的趋势，是模型正被嵌入到越来越完整的系统中：它需要上下文、工具、规则、反馈和外部连接共同支撑，才能在生产环境中稳定运行。

因此，后续值得持续关注的，不只是模型能力提升本身，而是连接器生态是否扩张、评测与治理是否标准化，以及头部公司能否把这些能力沉淀为稳定可收费的平台产品。

看这个专题时最该记住什么

Prompt engineering 主要解决输入表达问题，context engineering 主要解决信息组织问题，harness 主要解决系统执行与治理问题，MCP 则更接近其中的标准化连接层。

对头部公司而言，这意味着竞争边界正在从模型能力，扩展到连接器、工作流、评测和企业治理能力。对行业观察者而言，这通常比单次模型排行更接近长期平台价值。
